# Plan validation contract

Apply this structural review to the completed plan, not to the unfilled skeleton. These checks adapt the upstream check-plan helper without requiring Node, a particular repository layout, a vendor model, or a scheduler. Record PASS or a line/section-specific finding for every item. Do not claim an executable check ran unless an actual inspected checker ran.

1. **Document shape.** Require one H1 title, an introduction under ten nonblank lines, then How to read this, Program checklist, at least one PR section, Close the program, and appendices. Anything after Close the program is an appendix; include Prototype evidence.
2. **Reading contract.** Explain that one box is one unit of work, every box names its evidence, and only existing evidence checks a box. Name the actual installed execution resources and their versions. Include the verification rule below.
3. **Program order.** Preserve Arm the program, Spawn owners, PR mechanics, Verdict and merge, and Boot recipe in that order. Record actual installed-resource access, authorized audit capability or its absence, and status reporting. Never assume plugin files are in project trunk.
4. **PR block order.** Every PR section contains Depends on, Files, Build, You see, Verify unit, Verify live, Verify perf, Review gate, and Merge in that order. Dependencies name a PR or None. Files, Build, You see, Verify unit, and Merge each contain at least one evidence-bearing checkbox.
5. **Verification rule.** Each unit, live, and perf block opens with: Tests alone are not sufficient verification. A PR is verified only when its unit, live, and perf boxes are all checked.
6. **Live lanes.** Each PR has exactly ten uniquely numbered lanes, 1 through 10. Every lane names a concrete scenario, screenshot artifact path, and Pass when predicate. Record actual worker/isolation capabilities. At least one lane compares the same load-bearing scenario on trunk and head; if trunk lacks it, state that fact and gate the added behavior and user-visible end state. Missing independent workers or controls stay blocked.
7. **Performance evidence.** Require Metric, Probe, Baseline, and Rule checkboxes in that order. Measure the named metric at trunk and head with an interleaved probe and trunk baseline first. Name a numeric failure threshold. For unlike scenarios, use explicit absolute budgets for added work and the final user state; never invent a ratio.
8. **Review gate.** A None gate has no checkboxes and explains why no interaction changes. Otherwise require checkboxes for screenshots, video, and operator review. Stop at merge-ready until the required decision arrives.
9. **Merge and closure.** Record exact-head verdict, review/CI state, current base, patch validity, and the user's landing authority. Respect draft status. Close only when every required box has its actual evidence; blocked boxes cannot be marked passed. Preserve all four appendices for prototype evidence, alternatives, risks, and reading links.
10. **Prose and completeness.** Outside code and literal paths, check long dashes, curly quotes, and mid-sentence colons against the upstream writing rules. Fill every placeholder. Verify resource references through available host access. Report unresolved source, tool, reviewer, and scheduling gaps separately from passed checks.

The output is a per-PR box count and per-check findings, followed by total PR sections and unresolved problems. A structural pass does not authorize execution and is not evidence that a host ran the plan.
