# Statechart

Show how a product, protocol, service or design moves between states as a Mermaid statechart, with plain-language states and transitions that the person responsible for the behavior can review. Use the words of the person deciding the behavior, including observable stored values or messages. Keep code names out of labels; retain their provenance separately. A hidden effect that matters, such as a second charge while the screen still says Paying, must be visible in the state description. Start with few states and split them when needed to distinguish bugs or expose an important step that otherwise leaves the label unchanged.

## Establish capability and scope

This skills-only adaptation does not package or execute upstream's TypeScript statechart pipeline, executable view modules, TLC integration or Pele renderer. Do not run helpers from the vendored snapshot, infer a local skill path from a cloud resource, install dependencies automatically (including mise, Java/TLC or renderer npm packages), or claim a chart was generated or checked by those tools. Verify any existing project-local modeling, checking and rendering tools and the user's authorization before using them. Mapping modules are executable code, not inert labels; inspect and trust them before any authorized execution.

Use an authorized scratch directory or isolated copy; preserve the original model and application. Use a new empty output directory per run, and preserve prior outputs and files created concurrently; never overwrite them to force regeneration. Without a supported checker, provide a clearly labeled unverified Mermaid sketch or TLA+ skeleton and the missing checks. Manual translation does not guarantee that a chart and model stay synchronized. Missing tools do not turn a sketch into a checked result.

## Model to chart

Use only the commands supported by the verified tool actually available. Upstream 0.15.34 removed the old chart-to-model, baseline/fix comparison, expected-goal and cover command modes. The manual review practices below do not promise those commands or automatic comparison results.

1. Start from a copy of an existing TLA+ spec when available. Preserve existing invariants. To audit code against that spec, model what the code actually does in a separate copy and keep the agreed spec unchanged as the comparison baseline. Use the baseline authors' documented passing configuration, record its exact path and bounds, and disclose if it cannot be checked. Do not silently substitute the implementation model's configuration. Prefer shared state/step labels from variables present in both models. For a copy-only variable, test its presence explicitly and use a truthful alternate label for baseline states; never invent a value. When a model describes code, link every variable and action to inspectable code; each action represents one indivisible code step. Annotate each action condition with the actual source file and line that checks it, for example `\* pay.ts:120`; never invent a location.
2. Turn each agreed behavioral rule into an invariant with the person's sentence as its comment. A rule can concern a screen, request result, stored value or message. Add a missing model variable rather than dropping its rule. For code models, identify the code that changes that state; for design-only models, record assumptions without fabricating code provenance. For rules that apply after system activity settles, define `System` as the disjunction of non-user actions and use `Settled == ~ENABLED System`. For a narrower boundary, such as request completion, define a predicate for that point. Explain those assumptions. Never weaken a rule to make a chart pass.
3. Map user-visible states and transitions into readable labels. Record the user's actions separately from system steps. Preserve distinct code-path causes when different bugs reach the same screen. Optional visual groups must not conceal invariant violations.
4. If a fix is available, model the actual changed code separately. Compare the baseline, current implementation and proposed fix using available evidence. Distinguish fixed, still broken, newly broken, mixed, reachable-only-after-failure and unchecked outcomes explicitly; otherwise label status unknown or unverified. Do not reuse a fixed green/gray palette as proof. Explain each violated rule separately from group colors. A color alone is not proof; automatic fix comparison is not part of the new upstream pipeline.
5. Number each counterexample path in order. When the model describes code, replay each path against real code with one replay step per model action, through an authorized test or live reproduction. Drive user/client entry points or entry points reached by another system component and assert only outcomes they can observe. A test that merely asserts a flag it set itself or searches source text is not behavioral replay evidence. Separate the part demonstrated by execution from any part supported only by code reading. If code must be copied because it cannot be imported, identify the source commit and line range and list omitted behavior; do not present the copy as a full-target replay. If it does not reproduce, treat it as a possible modeling error until evidence shows otherwise. Correct the model, not the agreed rule. Disclose unavailable replay and distinguish model failures from confirmed product bugs. For a design without code, an actual checker trace is bounded design evidence, not a reproduced implementation bug; without a checker it remains an unverified sketch.

A rule absent from a comparison configuration is not checked there; never describe omission as holding or fixed. Distinguish temporal-property failures from state-invariant failures: a statechart can omit temporal counterexamples, so report them separately. Incomplete or crashed checker output cannot establish exhaustive success. Do not synthesize missing mapping variables from the baseline to make a comparison run. Report cross-model mapping shape or type mismatches instead of coercing them silently. Model-path replay is not real-code replay. Distinguish entry-step counts from shortest witness-path counts; do not interchange them. File/line citations and any heuristic citation scanner do not themselves prove that model conditions faithfully match the code.

For a reachability goal, an explicitly named negated-goal rule may be expected to break. Report its counterexample as a goal witness, not a product bug, even if a tool colors or narrates it as a violation. Never reclassify an ordinary failed rule as an expected goal after the fact. If reducing a large overview to shortest paths to settled states plus bug paths, list omitted states and transitions; a cover is not the full graph. Report temporal-property counterexamples separately and disclose checks limited to initial states; do not claim a full temporal check from that limit.

## Manual chart-first review

Draw the proposed behavior for review before implementing it. Use separate regions for independently changing aspects and represent stop/restart events as edges to their next observable state. Record one `%% never` rule with the person's sentence for each forbidden behavior. These annotations alone do not establish executable invariants.

The new upstream pipeline does not translate charts into models. With a separately available, inspected translation tool, create a TLA+ skeleton and check the agreed rules. Otherwise draft a clearly labeled unverified skeleton and explain the missing translation and checking steps. Take design-rule violations to the person who owns the behavior; do not silently revise the rules. Add real code guards and variables to the isolated model, recheck, and present each difference for a decision about whether the code or agreed chart needs correction.

## Keep abstraction and checking limits visible

Write `Next` as a disjunction of named actions so that the checker can identify steps. A terminal state with no outgoing step may be reported as deadlock even when it is an intended end. If the agreed semantics allow it, model an explicit unchanged self-step only in those terminal states and label it; do not suppress genuine deadlocks. Preserve an existing rule named `NoDeadlock` and distinguish a generated deadlock check such as `CHECK_DEADLOCK` from that rule.

Use plain reader-facing labels for flat states, parent states or independent parallel regions. Keep executable view functions pure: their answers must depend only on their arguments. Verify the tool's value representation rather than guessing how sequences or sets are encoded. Treat labels as data: escape them for the actual renderer so they cannot inject Mermaid directives or chart structure. Preserve guards on transitions and name a hidden deciding result in the step label. In a regions chart, do not replace generated cross-region conditions with ambiguous hand-written brackets. If factoring into regions invents a start state, transition or combination, use a faithful parent or flat chart instead. Label groups cannot establish correctness.

For each rule, distinguish a definite violation (all represented model states violate it) from a possible violation (only some do). Upstream aggregate `breaks` and `mayBreak` marks and their legends cannot establish per-rule certainty: a state that always breaks A but sometimes breaks B can receive one `breaks` mark listing both. Consult per-rule evidence and separate labels or report rows; claim a definite violation only for the rule actually always violated. Combining rules or regions can obscure which combination fails. Do not merge states that break different rules or turn a definite violation into an ambiguous one merely to simplify the picture. Keep bug paths and property-loop evidence visible. A repeated state is not necessarily a real loop: preserve any exits and checker evidence for repetition.

Aim for a readable chart, not an invented numeric guarantee. If hiding steps, keep every chart state reachable from a start, retain an outgoing arrow for every state with an outgoing model step, and hide all model steps behind an arrow or none. Preserve the evidence needed to distinguish failures. List omitted states and transitions and which steps are hidden. The visible graph is not necessarily the whole explored model.

With `VIEW` or `SYMMETRY`, a drawn state may represent several concrete states, and an arrow may target a representative instead of the concrete successor. Disclose that quotient and justify why the reduction preserves the particular property; matching a reduced-model result alone does not establish that. Report zero explored states explicitly rather than presenting a vacuous result as useful coverage. A checker may evaluate rules at a state beyond a `CONSTRAINT` or `ACTION_CONSTRAINT` without exploring it or checking deadlock there. Show an actual boundary witness when available, but do not infer behavior or deadlock freedom beyond the bound. A step excluded by an action constraint can still be part of a reported rule witness; do not silently remove it.

Separate the chart budget from the checking budget. In the reviewed upstream pipeline, more than 500 model states can produce only bug paths or no chart when no rule breaks. Later rule-checking passes after the first failure can stop at 100,000 distinct states. These are upstream tool limits, not bundled capabilities or promises about another checker. Report the actual configured bounds and every rule not checked because of a cap or error. A rule not checked may hold or break. Preserve any already established violation when later evaluation fails, while marking remaining rules and drawing coverage incomplete. The initial check has no universal time/state bound; use the actual authorized resource budget and report a stop without claiming completion. A later bounded pass can change variable ordering and the selected temporal counterexample; do not promise identical witness paths across runs. Keep the original-config checker output distinct from later per-rule runs. Do not call a missing chart a failed check or treat a chart as exhaustive exploration.

## Inspect and hand off

Provide Mermaid source. Follow [the guarded rendering guidance](references/render.md). If an authorized renderer is available, render the supported image format and inspect every image, including label readability, rule marks and numbered-path order. If rendering or visual inspection is unavailable, disclose that gap instead of claiming a visual pass.

For each issue, report the violated rule, numbered steps, code provenance, model-check result, real-code replay result and whether the proposed fix was verified. When comparing against a baseline spec, state whether each issue is already listed in its named configurations, recorded in its documented model omissions, or absent from both; disclose missing baseline evidence rather than guessing novelty. Do not report that a rule holds while any action condition lacks its source file and line when the model describes code. Distinguish confirmed bugs, modeling errors, design disagreements and unknown outcomes. Use counts from actual checker output; attach the actual report and raw checker outputs. Older `summary.json` or `stories.md` files are not promised by the new pipeline; use them only when the verified tool actually produced them. Never fabricate these artifacts or their counts. Include exact executed regeneration commands, or label unexecuted commands as proposed. State model bounds, omissions, unavailable checks and remaining decisions. Do not imply exhaustive application correctness from a bounded model.
